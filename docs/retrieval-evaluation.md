# AI 检索增量：范围、原始参考与复现

## 本轮只改检索层

保留现有模型、工具循环与精排调用预算。不增加 embedding、向量库、GraphRAG 或额外 LLM 查询改写调用，不修改普通搜索框、摘要接口或答案显示。

1. **召回**：关键词合并查询、去除常见提问套话的原始问题、前两条已有关键词变体，分词后去重，最多 4 路；RRF 用 `1 / (60 + rank)` 相加，固定块候选 20、单条候选 40。
2. **时间**：仅明确的近期倾向、且未显式指定日期时启用既有两天半衰期；历史问题按相关性。启发式不能替代完整的时间语义理解。
3. **精排**：每候选仍最多 120 字，但取命中原文附近而非无条件取块首。最终仍做相关性过滤，不改变为另一种模型或增加调用预算。
4. **上下文**：长块最多 17 条消息，分配给多个命中窗口；非连续片段用省略提示隔开。短块仍最多 30 条，最多返回 8 块。
5. **可追查性**：`ledger.retrievalTrace` 中的查询排名、分数、候选消息 ID、精排输入和最终证据 ID 可用来定位损失阶段。默认只随现有 API 的 ledger 返回，不写磁盘。

生成的别名只用于索引；精排优先读原文。已有话题标注仍以“话题标注”标题随最终片段提供，不能视为原话或已验证的事实。

## 参考与适配边界

- [Contextual Retrieval，Anthropic](https://www.anthropic.com/news/contextual-retrieval)：参考“片段应带可定位上下文”的原则；本轮没有重新实现文档级上下文生成，也不引用它的实验提升作为本项目成绩。
- [RRF，Microsoft Learn](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)：参考排名融合算法；本轮融合的是多个词面查询，不是稠密/稀疏混合检索，不依赖 Azure。
- [BEIR，2104.08663](https://arxiv.org/abs/2104.08663)：保留 BM25 基线、按多类任务评测；下述测试不是 BEIR 原数据或原评测成绩。
- [LongMemEval，2410.10813](https://arxiv.org/abs/2410.10813)：借鉴历史事实、时间及多处证据等题型；多人中文群聊与用户—助手历史不同，本轮没有运行 LongMemEval。
- [GraphRAG，2404.16130](https://arxiv.org/abs/2404.16130)：主要针对全局归纳问题，本轮不实现实体图或社区摘要。

以上原始页面已于 2026-09-28 核对。BEIR/LongMemEval/GraphRAG 本轮阅读的是原论文摘要；不是对全部论文实验的独立复现。

## 固定合成难例

`test/fixtures/qa-retrieval-cases.mjs` 生成 60 例，6 类各 10 个参数化变体：历史关键证据、新近度对照、原问题中的检索词被关键词遗漏、同一长块中分离的两处证据、块内较晚命中对照、无证据对照。

每例明确记录问题、工具参数、固定消息及必须出现的消息 ID。它们是根据已识别的失败机制设计的压力测试，不是独立采集的真实用户问题，10 个变体也不等于 10 种独立任务。

### 指标定义

- **整例证据齐全**：每个必需消息 ID 都进入检索片段的引用池；无证据题要求 `matchCount === 0`。
- **证据覆盖**：进入引用池的必需消息数 / 必需消息总数。60 例中 10 例无证据，其余共 60 条必需证据。
- **耗时**：单次离线工具执行的 P50/P95，仅诊断用，没有在线模型或网络耗时，且未控制 JIT/缓存，不用于宣称加速。
- **片段字符量**：逐题记录 `snippetChars`。两版使用相同的候选和消息条数上限，但字符/token 数不保证相同。

此处不报告回答正确率、引用支持率或模型幻觉率：没有运行最终回答模型。精排请求另由单测模拟，核查真正送出的候选文本和长度；模拟模型不能代表真实精排准确率。

同一份 4 块 × 24 条消息的精排输入探针中，命中记录均在块内第 21 条。旧版 4 个候选预览均不包含命中标识（0/4），新版均包含（4/4）；两侧都执行 1 次模拟调用，每候选文本都不超过 120 字。这是输入覆盖检查，不是模型排序准确率。

### 运行

```sh
npm run check
node scripts/benchmark-retrieval.mjs
```

对照 v1.27.1（`54b9a54`）：

```sh
baseline="$(mktemp -d)"
git archive 54b9a54 | tar -x -C "$baseline"
ln -s "$PWD/node_modules" "$baseline/node_modules"
node scripts/benchmark-retrieval.mjs --baseline-root "$baseline" --output /tmp/retrieval-comparison.json
```

仅从 Git 历史导出基线代码并共用同一套已安装依赖，不读取 `.env`、AI 配置或真实聊天记录。JSON 报告包含语料 SHA-256、逐题证据命中、片段字符量及新版诊断链。

| 指标 | v1.27.1 基线 | 本轮实现 |
| --- | ---: | ---: |
| 整例证据齐全 | 30 / 60 | 60 / 60 |
| 必需证据覆盖 | 30 / 60 | 60 / 60 |
| 历史 / 原问题遗漏 / 分离证据三类 | 各 0 / 10 | 各 10 / 10 |
| 新近度 / 块内晚命中 / 无证据对照三类 | 各 10 / 10 | 各 10 / 10 |

这只说明定向构造的机制用例通过，不能外推“真实准确率翻倍”。补充验证如下，仍未使用真实问题分布或真实回答模型。

## 补充样本与逐项消融

`test/fixtures/qa-retrieval-validation.mjs` 另含 18 个手工合成案例，覆盖中文/英文提问、编号、日期与人物过滤、旧决定、更新后的决定、媒体字段、无证据和纯语义鸿沟。它们没有用于初次实现，但已用于定位并修正问题，因此不再是盲测集，也不是外部真实用户数据。

```sh
node scripts/benchmark-retrieval-ablation.mjs --baseline-root "$baseline" --output /tmp/retrieval-ablation.json
```

该命令在独立子进程中运行旧版和本轮各策略，固定 UTC、问题、语料、工具参数与候选/片段条数上限。每例先预热 1 次，再测量 3 次，取中位数；精排使用保留全部候选的模拟返回，只检查输入覆盖，不能评估语义排序能力。消融替换仅在评测进程内生效，生产工具没有实验开关。

| 策略 | 18 例完整证据 | 必需证据条数 | 无证据题通过 | 精排预览包含目标信息 |
| --- | ---: | ---: | ---: | ---: |
| v1.27.1 基线 | 11/18 | 10/17 | 3/3 | 0/2 |
| 本轮完整策略 | 15/18 | 14/17 | 3/3 | 2/2 |
| 仅关键词查询 | 13/18 | 12/17 | 3/3 | 2/2 |
| 原问题不清理套话 | 13/18 | 14/17 | 1/3 | 2/2 |
| 恢复无条件时间衰减 | 12/18 | 11/17 | 3/3 | 2/2 |
| 恢复块首精排预览 | 15/18 | 14/17 | 3/3 | 0/2 |
| 恢复单命中窗口 | 14/18 | 13/17 | 3/3 | 2/2 |

发现并修正的退化：原问题中的“请问群里有没有”“Does anyone know”等套话曾造成 2 道无证据题返回无关候选；清理这类套话后，原先基线通过的题未发生退化。不能据此保证所有自然语言套话都被正确处理。

**保留的失败题，不删除也不改答案凑分：**`decision-rollback`（旧决定）、`url-original`（链接线索）、`known-semantic-gap`（无词面交集）。完整策略的原文片段共 7,928 字符，基线 7,771 字符；相同预算不代表实际上下文长度或成本完全相同。

模拟精排保留所有候选，所以块首预览消融不会改变最终证据覆盖；其 0/2 与 2/2 仅表示输入中是否包含目标信息。耗时统计只有本地计算和模拟请求，不是端到端模型延迟；不宣称更快。

## 保留的限制

- 查询改写依赖已有 Agent 关键词。没有词面交集且别名也未覆盖的语义问题仍会漏检。
- 多查询需要多次本地 BM25 计算，不承诺 CPU 开销不变；相同候选上限不等于相同实际 token 成本。
- 原问题带入常见词可能召回无关记录；120 字候选仍可能丢信息，尤其仅离线标注命中时原文锚点只能降级为块首。
- 不改变日期/人物过滤、按天加载索引和时间断层分块；没有解决跨日引用关系图、多账户隔离或索引更新策略。
- 诊断 trace 包含原文摘录，和已有 ledger 一样属于聊天数据，分享调试报告前必须脱敏。
